# 3.3 非功能需求分析

## 3.3.1 性能需求

系统性能需求定义了平台在响应时间、并发处理和资源利用方面的指标，确保用户获得流畅的使用体验。

响应时间方面，页面首次加载时间控制在 3 秒以内，这包括 DNS 解析、TCP 连接、SSL 握手、首字节时间和页面渲染全过程。API 接口响应时间控制在 500 毫秒以内，其中 95% 的请求应在 200 毫秒内完成。图片加载采用懒加载策略，首屏图片优先加载，非首屏图片在进入视口时触发加载，减少初始加载时间。

并发处理方面，系统应支持至少 100 个并发用户同时在线操作，峰值时段可扩展至 500 个并发用户。数据库连接池配置最大连接数为 50，确保高并发下数据库连接不成为瓶颈。WebSocket 连接数上限配置为 1000，满足社区级用户规模的实时通信需求。

资源利用方面，服务器 CPU 利用率在正常运行时控制在 60% 以下，内存利用率控制在 70% 以下，预留 30% 以上的资源缓冲应对流量突增。数据库查询执行时间超过 1 秒的慢查询自动记录至日志，便于后续索引优化。

如表 3.8 所示，性能需求指标明确了各场景下的量化目标。

表 3.8 性能需求指标

| 指标项 | 目标值 | 测量方法 | 优先级 |
|:------|:------|:--------|:------:|
| 页面首屏加载时间 | ≤ 3 秒 | Lighthouse 性能评分 | 高 |
| API 平均响应时间 | ≤ 200 毫秒 | 服务端日志统计 | 高 |
| API P95 响应时间 | ≤ 500 毫秒 | 服务端日志统计 | 高 |
| 并发在线用户数 | ≥ 100 人 | 压力测试 | 高 |
| 并发峰值用户数 | ≥ 500 人 | 压力测试 | 中 |
| 数据库连接池 | 50 连接 | 配置监控 | 高 |
| 慢查询比例 | ≤ 1% | 数据库慢查询日志 | 中 |

## 3.3.2 安全需求

系统安全需求涵盖身份认证、数据保护、访问控制和输入校验四个维度，确保平台和用户数据的安全性。

身份认证采用 JWT 无状态令牌机制，访问令牌有效期 2 小时，刷新令牌有效期 7 天。令牌使用 HS256 算法签名，密钥长度不少于 256 位，存储于服务端环境变量，不提交至版本控制。密码采用 BCrypt 算法加密存储，工作因子设置为 12，确保即使数据库泄露也无法逆向破解。

数据保护方面，用户手机号、支付宝账号等敏感信息在数据库中加密存储。图片等静态资源通过独立域名访问，配置防盗链策略防止外部盗用。HTTPS 协议全站启用，TLS 版本不低于 1.2，确保传输层数据加密。

访问控制基于 RBAC（基于角色的访问控制）模型，定义 USER 和 ADMIN 两个角色。普通用户只能访问个人相关数据和公开数据，管理员可访问后台管理功能。敏感操作（如支付、删除）需二次确认，防止误操作和 CSRF 攻击。

输入校验方面，所有用户输入经过服务端校验，防止 SQL 注入、XSS 攻击和命令注入。文件上传限制类型和大小，图片文件进行格式校验和内容扫描，防止上传恶意文件。

如表 3.9 所示，安全需求明确了各维度的防护措施。

表 3.9 安全需求措施

| 安全维度 | 防护措施 | 实现方式 | 优先级 |
|:--------|:--------|:--------|:------:|
| 身份认证 | JWT 令牌 | 签名验证、过期检查 | 高 |
| 密码存储 | 单向加密 | BCrypt 哈希 | 高 |
| 传输加密 | HTTPS | TLS 1.2+ 证书 | 高 |
| 敏感数据 | 加密存储 | AES 加密 | 高 |
| 访问控制 | RBAC | Spring Security | 高 |
| 输入校验 | 白名单过滤 | 正则表达式、长度限制 | 高 |
| 文件上传 | 类型限制 | MIME 校验、大小限制 | 高 |
| 防重放攻击 | 请求幂等 | 唯一请求 ID | 中 |

## 3.3.3 可用性需求

系统可用性需求定义了平台在可靠性、可维护性和用户体验方面的指标，确保服务持续稳定运行。

可靠性方面，系统年度可用性目标为 99.5%，即全年计划外停机时间不超过 43.8 小时。数据库每日自动备份，备份文件保留 7 天，支持任意时间点的数据恢复。关键业务操作（支付、退款）记录完整日志，支持操作追溯和审计。

可维护性方面，代码遵循统一的编码规范，关键业务逻辑添加注释说明。配置信息外部化，通过配置文件或环境变量管理，避免硬编码。日志分级管理，ERROR 级别日志实时告警，WARN 级别日志每日汇总，INFO 级别日志按周归档。

用户体验方面，界面设计遵循一致性原则，相同功能在不同页面保持相同的交互方式。错误提示使用用户友好的语言，避免展示技术细节和异常堆栈。空状态提供引导操作，帮助用户快速进入下一步。加载状态提供进度反馈，超过 3 秒的加载显示骨架屏或进度条。

如表 3.10 所示，可用性需求明确了各维度的量化目标。

表 3.10 可用性需求指标

| 指标项 | 目标值 | 测量方法 | 优先级 |
|:------|:------|:--------|:------:|
| 年度可用性 | ≥ 99.5% | 服务监控统计 | 高 |
| 数据备份频率 | 每日 | 自动备份任务 | 高 |
| 备份保留周期 | 7 天 | 备份存储策略 | 高 |
| 错误恢复时间 | ≤ 30 分钟 | 故障演练 | 高 |
| 页面错误率 | ≤ 0.1% | 前端监控 | 中 |
| 用户操作成功率 | ≥ 99% | 业务日志统计 | 高 |

## 3.3.4 兼容性需求

系统兼容性需求定义了平台在不同设备和浏览器环境下的适配要求，确保广泛的用户覆盖。

浏览器兼容方面，前端应用支持 Chrome 90+、Firefox 88+、Safari 14+、Edge 90+ 等现代浏览器。不支持 Internet Explorer 浏览器，访问时提示用户升级。CSS 采用 TailwindCSS 框架，自动处理浏览器前缀和兼容性。JavaScript 使用 ES2020 语法，通过 Vite 构建工具转译为兼容代码。

设备兼容方面，前端采用响应式设计，适配桌面端（≥1024px）、平板端（768px-1023px）和移动端（＜768px）三种屏幕尺寸。移动端优化触摸交互，按钮尺寸不小于 44×44 像素，支持手势滑动操作。图片采用响应式加载，根据设备像素比提供不同分辨率版本。

后端兼容方面，服务端接口遵循 RESTful 规范，返回 JSON 格式数据，与客户端技术栈无关。数据库使用标准 SQL，避免使用特定数据库的专有语法，便于后期迁移。
