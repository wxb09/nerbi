# 4.3 核心业务流程与时序设计

## 4.3.1 借阅管理流程设计

借阅管理是平台最核心的业务流程，涉及借入者、借出者、支付系统和消息通知等多个参与方。如图4.4所示，该流程由六个连续阶段构成完整的借用闭环。

```mermaid
flowchart LR
    A[提交申请] --> B[借出者审批]
    B -->|拒绝| C[流程结束]
    B -->|通过| D[借入者支付]
    D --> E[确认取货]
    E --> F[申请归还]
    F --> G[确认归还]
    G --> H[退还押金]
    H --> I[流程结束]
```

图4.4 借阅管理整体流程图

每个阶段存在严格的前置条件校验。提交申请阶段校验物品状态必须为可借用，且申请者不能是物品所有者。审批阶段校验操作者必须是物品所有者。支付阶段校验借阅状态必须为已批准，且支付金额大于零。确认归还阶段校验借阅状态必须为归还待确认，且操作者为物品所有者。

如图4.5所示，借阅状态在数据库层面维护，各状态之间的合法转换关系通过状态机进行约束。

```mermaid
stateDiagram-v2
    [*] --> PENDING: 提交申请
    PENDING --> APPROVED: 审批通过
    PENDING --> REJECTED: 审批拒绝
    APPROVED --> ACTIVE: 支付成功
    APPROVED --> CANCELLED: 取消申请
    ACTIVE --> RETURN_REQUESTED: 申请归还
    RETURN_REQUESTED --> RETURNED: 确认归还
    REJECTED --> [*]
    CANCELLED --> [*]
    RETURNED --> [*]
```

图4.5 借阅状态机转换图

如图4.6所示，借阅申请时序图展示了借入者提交申请到借出者完成审批的完整交互过程。前端首先携带JWT令牌提交申请数据，Controller解析当前用户身份后调用Service创建借阅记录，Service校验物品状态和所有者关系，通过校验后保存记录并发送审批通知给借出者。

```mermaid
sequenceDiagram
    actor U1 as 借入者
    participant F1 as 前端
    participant C1 as BorrowController
    participant S1 as BorrowService
    participant R1 as BorrowRepository
    participant M1 as MessageService
    participant F2 as 借出者前端

    U1->>F1: 填写借阅申请
    F1->>C1: POST /api/borrows<br/>Authorization: Bearer token
    C1->>C1: 解析JWT获取用户ID
    C1->>S1: createBorrow(request, userId)
    S1->>S1: 校验物品状态为AVAILABLE
    S1->>S1: 校验申请者≠所有者
    S1->>R1: save(borrow)
    R1-->>S1: 返回保存结果
    S1->>M1: 发送审批通知
    M1->>F2: WebSocket推送
    S1-->>C1: 返回借阅ID
    C1-->>F1: ApiResponse.ok(id)
    F1-->>U1: 显示申请成功
    F2-->>U1: 显示新通知角标
```

图4.6 借阅申请时序图

如图4.7所示，支付流程时序图展示了从创建支付订单到异步回调处理的完整资金交互。借阅审批通过后，借入者触发支付，服务端创建支付订单并调用支付宝接口生成支付表单，前端渲染表单跳转至支付宝页面。用户完成支付后，支付宝服务端异步通知应用服务端，服务端验签通过后更新支付状态和借阅状态。

```mermaid
sequenceDiagram
    actor U as 借入者
    participant F as 前端
    participant PC as PaymentController
    participant PS as PaymentService
    participant PR as PaymentRepository
    participant AC as AlipayClient
    participant AP as 支付宝网关
    participant BR as BorrowRepository

    U->>F: 点击"去支付"
    F->>PC: POST /api/payments/create
    PC->>PS: createPayment(borrowId, userId)
    PS->>PS: 计算租金和押金
    PS->>PR: save(payment)
    PS->>AC: 调用支付宝下单API
    AC->>AP: 发送下单请求
    AP-->>AC: 返回支付表单HTML
    AC-->>PS: 返回表单
    PS-->>PC: 返回表单数据
    PC-->>F: 返回支付表单
    F->>F: 渲染表单并自动提交
    F->>AP: 跳转至支付宝支付页
    U->>AP: 完成支付
    AP->>PC: 异步通知 POST /notify
    PC->>PS: handleNotify(params)
    PS->>AC: 验签
    AC-->>PS: 验签通过
    PS->>PR: updateStatus(PAID)
    PS->>BR: updateBorrowStatus(ACTIVE)
    PS-->>PC: 处理成功
    PC-->>AP: 返回"success"
    AP-->>F: 同步跳转回前端
```

## 4.3.2 论坛内容发布流程设计

论坛内容发布流程包含敏感词自动检测机制，确保社区内容符合规范。如图4.8所示，用户提交帖子或评论后，内容首先经过敏感词审核服务检测，通过检测的内容正常保存并展示，命中敏感词的内容被拦截并记录审核日志，同时向用户返回内容违规提示。

```mermaid
flowchart TD
    A[用户提交内容] --> B[敏感词检测]
    B -->|未命中| C[保存内容]
    B -->|命中| D[记录审核日志]
    C --> E[返回成功]
    D --> F[返回违规提示]
```

图4.8 内容发布审核流程图

如图4.9所示，帖子发布时序图展示了从用户编辑内容到帖子成功创建或拦截的完整交互。用户在前端编辑器输入内容并选择类型标签，前端提交至PostController，Controller调用PostService处理业务逻辑，Service首先调用敏感词审核服务进行内容检测，通过后将帖子保存至数据库并返回成功响应。

```mermaid
sequenceDiagram
    actor U as 用户
    participant F as 前端
    participant PC as PostController
    participant PS as PostService
    participant AS as AuditService
    participant PR as PostRepository

    U->>F: 编辑帖子内容
    F->>F: 选择类型和标签
    U->>F: 点击发布
    F->>PC: POST /api/forum/posts
    PC->>PC: 解析JWT获取用户ID
    PC->>PS: createPost(request, userId)
    PS->>AS: auditText(content)
    AS->>AS: 匹配敏感词库
    alt 内容通过
        AS-->>PS: 返回通过结果
        PS->>PR: save(post)
        PR-->>PS: 返回帖子ID
        PS-->>PC: 返回ID
        PC-->>F: ApiResponse.ok(id)
        F-->>U: 显示发布成功
    else 命中敏感词
        AS-->>PS: 返回拦截结果
        PS->>AS: recordAuditLog(reject)
        PS-->>PC: 抛出BusinessException
        PC-->>F: ApiResponse.fail(8001)
        F-->>U: 显示内容违规提示
    end
```

## 4.3.3 举报处理流程设计

举报处理流程连接普通用户和管理员，形成内容治理的闭环。如图4.10所示，用户在浏览帖子时发现违规内容可提交举报，填写举报原因后创建举报记录。管理员在后台查看待处理举报列表，点击处理后可选择删除违规内容或驳回无效举报，处理结果同步更新举报记录状态并通知举报人。

```mermaid
flowchart LR
    A[用户发现违规内容] --> B[提交举报]
    B --> C[创建举报记录]
    C --> D[管理员查看列表]
    D --> E{处理决策}
    E -->|删除内容| F[更新帖子状态]
    E -->|驳回举报| G[更新举报状态]
    F --> H[通知举报人]
    G --> H
```

图4.10 举报处理流程图

如图4.11所示，举报处理时序图展示了从用户提交举报到管理员完成处理的完整交互链路。用户在前端点击帖子举报按钮，填写举报原因后提交至ReportController，Controller创建举报记录并保存。管理员在后台页面查询待处理列表，选择处理操作后更新举报记录和帖子状态，同时通过消息服务通知举报人处理结果。

```mermaid
sequenceDiagram
    actor U1 as 举报用户
    participant F1 as 前端
    participant RC as ReportController
    participant RS as ReportService
    participant RR as ReportRepository
    participant AR as AuditLogRepository
    actor U2 as 管理员
    participant F2 as 管理后台
    participant MS as MessageService
    participant F3 as 被通知前端

    U1->>F1: 点击举报按钮
    F1->>F1: 填写举报原因
    U1->>F1: 提交举报
    F1->>RC: POST /api/reports
    RC->>RS: createReport(request, userId)
    RS->>RR: save(report)
    RR-->>RS: 返回记录
    RS-->>RC: 返回成功
    RC-->>F1: ApiResponse.ok
    F1-->>U1: 显示举报已提交

    U2->>F2: 查看举报列表
    F2->>RC: GET /api/admin/reports
    RC->>RS: getPendingReports()
    RS->>RR: findByStatus(PENDING)
    RR-->>RS: 返回列表
    RS-->>RC: 返回数据
    RC-->>F2: 返回列表数据

    U2->>F2: 选择处理操作
    F2->>RC: POST /api/admin/reports/{id}/handle
    RC->>RS: handleReport(id, action, adminId)
    alt 删除内容
        RS->>RS: 更新帖子状态为DELETED
        RS->>AR: 记录处理日志
    else 驳回举报
        RS->>AR: 记录驳回日志
    end
    RS->>RR: updateStatus(RESOLVED/REJECTED)
    RS->>MS: 通知举报人
    MS->>F3: WebSocket推送
    RS-->>RC: 返回结果
    RC-->>F2: 返回成功
    F2-->>U2: 显示处理完成
```

## 4.3.4 消息通知推送流程设计

消息通知模块采用WebSocket协议实现服务端主动推送。如图4.12所示，当业务事件发生时，消息服务创建通知记录并查询接收者在线状态，若接收者在线则通过WebSocket连接实时推送，若离线则消息保留至数据库待用户上线后拉取。

```mermaid
flowchart TD
    A[业务事件触发] --> B[创建消息记录]
    B --> C{接收者在线?}
    C -->|是| D[WebSocket实时推送]
    C -->|否| E[消息存入数据库]
    D --> F[前端显示通知]
    E --> G[用户上线后拉取]
```

图4.12 消息通知推送流程图

如图4.13所示，WebSocket连接建立时序图展示了客户端从发起连接到完成身份认证的完整握手过程。客户端首先发起WebSocket连接请求，服务端拦截器从URL参数中提取JWT令牌进行校验，校验通过后建立持久连接并将用户ID与Session绑定，后续服务端可通过该Session向指定用户推送消息。

```mermaid
sequenceDiagram
    actor U as 用户
    participant F as 前端
    participant WS as WebSocketHandler
    participant IC as AuthInterceptor
    participant SS as SessionStore
    participant MS as MessageService
    participant MR as MessageRepository

    U->>F: 登录成功
    F->>F: 获取JWT令牌
    F->>WS: 发起WebSocket连接<br/>携带token参数
    WS->>IC: 拦截连接请求
    IC->>IC: 解析并校验JWT
    alt 校验通过
        IC-->>WS: 继续建立连接
        WS->>SS: 绑定userId与session
        SS-->>WS: 绑定成功
        WS-->>F: 连接建立
        F-->>U: 显示连接状态

        Note over MS,MR: 业务事件触发推送
        MS->>MR: save(message)
        MS->>SS: 查询用户session
        SS-->>MS: 返回session
        MS->>WS: 发送消息
        WS->>F: WebSocket推送
        F->>F: 显示通知角标
    else 校验失败
        IC-->>WS: 拒绝连接
        WS-->>F: 连接失败
        F-->>U: 显示重连按钮
    end
```
